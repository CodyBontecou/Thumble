# Durable configuration ledger v1

The Bun service now owns a protected SQLite source ledger through the portable `ConfigurationRepository` application port. The host adapter is `@thumble/storage`. It persists exact lossless JSON source and atomic operation receipts. This is the storage seam for the rewrite, not activation of a profile format or migration of the retained authority. The active receiver configuration remains ephemeral; typed owned-document validation, scoped CLI/MCP writes, assets and runtime publication still require implementation. No generic raw-source write tool is exposed.

## Ownership and protection

The development ledger lives at `configuration-v1.sqlite3` inside the user-restricted rewrite runtime namespace. The bundled native helper's `secure-configuration` mode protects that fixed file and an existing rollback journal with the same Unix ownership/mode and Windows user/SYSTEM ACL policy as other native state. It accepts no extra filename argument, does not truncate existing data and does not depend on the desktop GUI. The adapter rejects unsafe main/journal links and orphan auxiliary files before helper admission. WAL/SHM are refused: this schema uses rollback journals only. SQLite opens the already protected main file with `SQLITE_OPEN_NOFOLLOW`.

One SQLite connection holds exclusive locking mode and an explicit exclusive transaction/commit on every open, including an idle reopened head. It retains the writer lease until close. All product callers must go through the active service; stopped CLI edits must use the same service/application path rather than open the database directly. Adapter-level tests use direct access solely to seed isolated fixtures. A process exit releases the OS lease. The service closes the ledger before removing its endpoint and waits for native owner exit before allowing restart. Startup failure closes already-created owners; an unconfirmed close never reports a successful restart barrier.

Version 1 uses application ID `0x54484346`, user version 1, exact STRICT table definitions, 4096-byte pages, synchronous FULL and DELETE journaling. It checks schema identity, SQLite quick-check and the current source/head receipt before admission. Unknown schemas or corrupt source/hash/receipt heads fail instead of being regenerated or overwritten. The maximum is 65,536 pages (256 MiB); a smaller test/host resource limit is permitted. Resource exhaustion returns a typed failure and preserves committed state. There is no receipt eviction or implicit revision reset.

## Transactions and retry semantics

An application commit supplies an operation ID, canonical uint64 expected revision, a server-derived payload fingerprint, a validated immutable source and up to 256 affected identifiers. Identifier arrays must be dense data values with no duplicates/accessors. Trusted use cases must check caller capability and typed document semantics and compute the fingerprint from the complete canonical request/scope; neither a raw source mutation nor caller-selected fingerprint is a safe RPC contract.

The transaction first looks up the operation ID. An identical fingerprint returns the original immutable receipt, even after later commits. A different fingerprint returns `operation_id_reused`. Otherwise the transaction compares current revision (zero for an empty ledger), advances it exactly as a decimal uint64 string, writes the source and receipt in the same SQLite transaction, and returns the receipt only after commit. Stale revisions do not reserve operation IDs. Exhausted uint64 revisions fail without wrapping. No counter crosses a JavaScript/SQLite floating-point conversion.

Receipts contain version 1, operation ID, resulting revision, content hash and affected identifiers. They have no full-source or credential fields. Source hashing uses the [lossless JSON v1](rewrite-lossless-json-v1.md) prefix and canonical source text. Reopening verifies the stored source hash and its latest receipt. Historical receipts remain historical proof; replay does not mean the current document still equals that operation's result.

## Verification and limits

Tests exercise separate-process writer ownership and abrupt death after an acknowledged commit, exact full-width source preservation across reopen, identical retries after later writes, changed-fingerprint rejection, stale CAS without ID reservation, safe-integer and uint64 revision boundaries, protected file modes, unsafe links/auxiliary files, extra helper arguments, and refusal of foreign or forged schemas/corrupt hashes. A real SQLite page limit forces a large receipt insert to fail after a source update; reopening proves both the old source and absence of the failed receipt. Service process tests require the writer lease released at endpoint disappearance and prove stored source survives restart without activating input. Standalone packaging starts the same ledger with no checkout or Bun on PATH.

Local checks pass 90 portable/host tests, 80 Rust unit and 12 process tests, Clippy, standalone packaging (41 assertions), formatter/types/generated/import boundaries. Bun's built-in SQLite reports 3.51.0 locally; the native trust ledger uses its separately bundled engine and namespace. Windows files/locks and native provider compatibility require hosted checks for this source. No retained Swift/shared model changed, and retained stack-safety/cutover acceptance remains open. This does not complete the full configuration application, MCP facade or any launch gate.
