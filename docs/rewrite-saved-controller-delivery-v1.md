# Revision-pinned saved controller delivery

The saved controls endpoint is distinct from metadata catalog browsing. It reads the already selected saved profile for an **explicitly bound recording generation**; it never activates a receiver or substitutes a newer saved source. See [saved runtime binding](rewrite-saved-runtime-binding-v1.md) and the [supported projection subset](rewrite-saved-controller-map-v1.md).

A control-v8 `management` connection authenticates with the existing pinned TLS and phone credential flow. Its single `configuration-controls` request supplies the expected saved configuration revision/storage source hash/canonical profile UUID, active native generation/revision, and the input surface's logical safe width/height. Metadata catalog role v7 and input role v6 remain separate. Management authentication grants no input session, grant key or output capability.

The native host checks the saved binding using a separate bounded native read, forwards a correlated private `phone-controls` event to the parent, and rechecks its binding and authorization before delivery. The parent delegates the read to the sole configuration child. That child verifies the current repository revision/source hash and selected profile, materializes content-addressed assets with byte-count/hash verification, admits the owned document, and runs the pure saved-controller projection. Unsupported interactive semantics fail closed. No database/image/resource decoding runs on input heartbeat IO.

The reply pins both **storage `sourceHash`** (catalog `contentHash`, canonical and domain-separated) and **`configurationSha256`** (SHA-256 of the exact materialized owned-document UTF-8 text). These hashes have different meanings. Native input generation/revision are independent of the saved configuration revision. A request must match all applicable identities; missing/expired/replaced/unbound native state or unavailable current saved source requires explicit reactivation. There is no historical source reconstruction or automatic latest-profile fallback.

A successful owner projection is an immutable snapshot for the already activated native pin. If storage changes after projection but before delivery or the input grant, the old projected map may still install while that exact native pin/generation/revision remains active. Storage writes do not silently retire or replace that activation, and the grant does not recheck current storage freshness. A later map read can fail `saved_map_reactivation_required` because the old source is no longer available. Applying edited storage requires explicit saved activation; native replacement/expiry and authorization changes still invalidate pending admission.

The public reply is one flat scalar object. A successful result includes identity/pins, the exact requested viewport strings, `controlCount`, and indexed `control0Id`, `control0Action`, `control0X/Y/Width/Height` fields. Haptics are either absent or include all five indexed style/pattern/intensity/sharpness/duration fields. Coordinates, haptic numeric values and viewport dimensions are bounded ASCII decimal strings; scientific notation from JavaScript serialization is supported, with finite/range checks. Viewport text is echoed byte-for-byte, including `874.0` versus `874`; conversion never quantizes a hit boundary merely to fit a transport.

The existing 65,536-byte frame bound is unchanged. Only this new envelope permits up to 848 fields; legacy enrollment and catalog shapes remain unchanged. Results reserve private/TLS envelope space and validate the existing native `ControlMap` contract. One to 64 controls is an upper bound, not permission to send an oversized frame. No source document, asset bytes, paths or credentials enter the public map reply.

There is one bounded underlying configuration read. The phone-facing parent deadline is two seconds; a slow read retains its thirty-second owner-health budget and keeps the read slot busy until it actually finishes. A timed-out phone request cannot cause overlapping synchronous child work. Late responses remain correlated and cannot satisfy a successor. Sampling/renewal use their independent input paths and original safety deadlines. Fixed errors are `saved_map_busy`, `saved_map_timeout`, `saved_map_unavailable`, `saved_map_reactivation_required`, `saved_map_unsupported_profile` and `saved_map_response_too_large`.

Phone native clients must validate the reply against their request, current connection/authority and actual logical surface bounds, then pass the map through existing native admission/grant rechecks before installing it. Layout/attempt changes, backgrounding, rotation and disposal invalidate pending work. The installed native map is the input authority; React may receive a public copy only for presentation. Practice retains its local standard controller. Connected saved-map failures must leave controls unavailable rather than installing the standard template. Renderer/skin appearance parity and physical/gameplay acceptance remain separate gates.

The shared synthetic wire fixture is `Rewrite/packages/fixtures/saved-controller-control-v8.json`. `saved-controller-v1.json` is a complete synthetic owned-v5 source with disjoint first/selected controls and a selected rectangular South button. Portable tests consume both fixtures, verify source/epoch/viewport pinning and strict fields/haptics, exercise actual saved selection and retained logical dimensions, verify external resource materialization and corruption failure, and prove timeout retains bounded underlying work. Full SDK/service/device evidence is recorded separately; these tests alone establish no physical-input or gameplay acceptance.
