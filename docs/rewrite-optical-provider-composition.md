# Headless optical provider composition

Capture is disabled by default. No capture owner or native helper is created by an ordinary service launch. A locally authorized operator may launch `service start --capture-helper ABSOLUTE_EXECUTABLE` (or `service run`); the service validates and resolves that executable path once. IPC and MCP requests cannot select executables, files, window handles, processes or arbitrary desktop sources. Changing launch options requires stopping the existing service first.

With that service running, `wow capture-start --source world-of-warcraft` allocates a service-local opaque source and generation and requests one capture. `wow capture-request` explicitly requests another; `wow capture-status` returns bounded receipt metadata, and `wow capture-stop` invalidates it and retires the provider. These commands use the existing authenticated local endpoint. MCP always offers `wow_capture_status`; start/request/stop tools require `mcp serve --allow-wow-capture` in addition to the helper-enabled service. This is single-frame acquisition plumbing, not automatic live sync or configuration refresh.

The TypeScript capture owner is a separate process. It owns the frozen supervisor, its injected monotonic clock and native provider. Large frame/PNG responses and decompression never run in the input-renewal process. The parent receives only fixed status, opaque source/generation/receipt identity, monotonic observation time, byte length and SHA-256 metadata. Receipt expiry and invalidation remain authoritative in the owner. `ready` means a receipt is available; its kind distinguishes an actual frame from a fixed permission/visibility/error status. No source pixels, PNG bytes, frame payloads, private process/window identities or helper paths appear in public status. A capture receipt does not renew game freshness, acknowledge an observer, change saved configuration, activate a profile or emit input.

Each native provider uses a fresh child for the selected generation and one request at a time. It validates the u32 big-endian response length before allocation, then enforces existing strict receipt correlation and ASCII/JSON/base64 limits. It bounds and discards stderr without logging it. Unexpected child failure invalidates published metadata. Shutdown/replacement requires the child's actual close event; a supervisor stop timeout retains the provider slot rather than authorizing overlap. A hung capture times out under the existing two-second supervisor budget. Capture-owner failure affects capture requests; it does not stop or borrow the input owner. A service restart is required after capture-owner process failure.

The required production atlas decoder validates PNG signature, 256-square dimensions, chunk count/CRCs and the existing two-MiB encoded bound. It supports only noninterlaced eight-bit RGB or RGBA. Bounded zlib inflation must produce exactly the expected scanline length (at most262400 bytes), consume all compressed bytes and reject invalid filters or trailing data. All five PNG filters and RGB transparency are reconstructed into exactly262144 RGBA bytes. Invalid palettes/transparency metadata, reserved chunk names and animated PNG extensions are rejected. No unbounded general image library, file access or native screenshot is involved in this decoder.

`wow permission-status --capture-helper ABSOLUTE_EXECUTABLE` explicitly runs only the helper's `--status`; `wow request-permission` explicitly runs `--request-permission`. Neither is called by service/capture status. Permission commands have a separate bounded4096-byte frame and three-second caller deadline. Their exact reply types differ from capture receipts. Possible permission statuses are `authorized`, `permission-required`, `not-inspected` and `unavailable`; API availability alone must not imply OS authorization. Permission request has no source/window selector and cannot begin capture. Service status retains `permission:not-inspected` rather than claiming a separately inspected authorization result.

The macOS helper is built separately from `Rewrite/native/wow-capture-macos`; it is not automatically installed or signed by the default CLI package. The operator supplies its path explicitly. Its private pre/post process-start, executable-file, window, dimensions and scale checks remain intact. No automated composition gate invokes actual capture, TCC preflight or permission APIs: fake children and synthetic PNGs exercise the process/protocol/decoder path, and native package compilation remains separate. Real WoW windows, real TCC behavior/signing, Windows provider acceptance, observation-to-authority mapping and gameplay/live-sync launch acceptance remain pending. Manual refresh is still required until that later authority seam exists.
