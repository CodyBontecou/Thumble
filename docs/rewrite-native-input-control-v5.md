# Native input control version 5

Version 5 adds receiver-owned UDP input alongside the version-4 reliable TLS path. Clients must explicitly negotiate hello version 5. Versions 2–4 retain their prior meaning; existing native phone clients continue to select 3 or 4. This implements the host seam, with recording output only. Native phone UDP senders and automatic fallback remain pending.

The headless host binds one ephemeral UDP port on the same IP as the explicitly configured TLS listener. Only an authenticated version-5 grant reveals that port. There are no UDP replies. The grant retains every version-4 field except `transport:"udp+tls"` and an additional numeric `udpPort` (1–65535). TLS connection binding, receiver-generated key/session/prefix, exact configuration generation/revision, trust epoch and remaining authenticated lifetime remain authoritative. Secrets stay between native processes and the native phone client.

A UDP datagram contains exactly the existing 108-byte sealed input packet. The host reads the public session/generation/sequence header only for bounded routing and coalescing; the independent receiver authenticates AES-GCM, enforces replay/counter policy and accepts the full state before progress advances. Both UDP and TLS use the same grant and monotonically increasing nonce sequence. Switching transport cannot reset a counter, replay a queue, renew configuration ownership or resurrect an expired source. A caller retransmitting a packet must reuse identical ciphertext, never encrypt different state with a reused nonce.

Version 5 adds the strict request `{"version":1,"command":"input-status","connectionId":"<exact TLS binding>","sessionId":"<exact grant>"}`. Its reply contains exactly version, command, connectionId, sessionId, active, decimal generation/revision, lastAcceptedSequence (decimal string or null), and inputEnabled:false. Progress reflects receiver-acknowledged admission across both transports. Configuration/deadline checks determine active status; a status request does not renew input TTL. An ordered control reply cannot prove arbitrary UDP delivery. A future phone sender must use progress to detect loss, choose reliable fallback before TTL expires, and terminally retire if its source is inactive.

On version 5, duplicate/older sequences at or below acknowledged progress have no effect and do not refresh TTL. This permits late in-flight traffic during transport overlap. A newer malformed packet is rejected by native admission; UDP drops the error without replying, whereas reliable protocol errors close the control owner. Version 4 retains its existing strict replay behavior. The version-5 progress budget is 65,536 acknowledged packets across both transports, below the cryptographic counter limit. TLS input frames have their separate 65,536-frame bound, including stale frames. Version-5 controls are capped at 1,024 per 60-second authentication lifetime; version 4 remains capped at 128.

## Bounds and retirement

One native UDP worker reads at most 64 datagrams per cycle into a 109-byte buffer, rejecting truncated/oversized packets. It retains at most four known-session snapshots, choosing the largest public sequence in each cycle, and attempts at most 240 deliveries per second. A forged public header can cause a drop; it cannot create accepted progress or input. Traffic is intentionally lossy under load or mutation-gate contention. No unbounded packet queue or sender-address registry exists. The worker yields between bounded private receiver RPCs.

Every UDP delivery obtains the shared trust mutation fence without waiting, rechecks credential epoch/expiry and the monotonic grant deadline, then waits for native admission. Revocation and re-enrollment use the same fence and retain registry entries until native release acknowledgment. Listener stop drops UDP/TLS sockets, rejects queued old-listener admission, and waits for all registered native source releases before claiming success. Failed release is reported as unconfirmed. The independent receiver owner lease and input TTL remain unchanged.

## Verification and limits

Separate-process tests cover UDP held state, reliable neutral fallback, late packets in both directions, bad AEAD, oversized/unknown sessions, duplicate traffic failing to refresh TTL, fresh traffic failing to resurrect expired input, revocation, re-enrollment, old-key isolation and listener-stop release/port closure. UDP probes retransmit identical ciphertext until reliable progress confirms admission, accounting for intentional drops under contention.

The native server passes 79 unit and 12 process tests plus Clippy. Existing version-4 phone compatibility passes 55 Swift tests and Android native tests/build/lint. These local checks do not certify physical output, real network loss/latency, Windows runtime, phone version-5 transport selection, gameplay or optical live sync. Sixty-second grants and authentication still require a production renewal design. All launch acceptance gates remain open.

## Native phone decoding seam

Swift and Kotlin now decode a version-5 grant only with explicit datagram opt-in. Ports must be unsigned integers 1–65535, with exactly the UDP grant fields and transport name. Version-4 callers continue rejecting these grants. Native progress decoding requires exact connection/session/configuration, rejects unknown fields, counter values outside the cryptographic bound, acknowledgments beyond the latest offered packet, and rollback (including null after accepted progress). An inactive receipt remains terminal metadata for callers to retire the source. Flat JSON null is permitted only with explicit parser opt-in for progress; enrollment/control defaults continue rejecting it. This seam does not yet enable version-5 negotiation or UDP phone transmission.
