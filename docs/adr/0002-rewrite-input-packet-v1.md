# Native input packet v1

Status: accepted wire layout for isolated implementation and conformance tests; no real-input or production security certification.

Phone-to-receiver input uses one 108-byte AES-256-GCM packet. The 40-byte authenticated header is `THI1` (4 bytes), four zero reserved bytes, a 16-byte nonzero random session identifier, a nonzero unsigned 64-bit activation generation, and an unsigned 64-bit sequence. Integers are little endian. Unsupported magic/reserved bits, session/generation mismatches and lengths other than 108 fail closed. This is separate from retained `PP` frames and from document/control versions.

The 52-byte plaintext is an unsigned little-endian 32-bit semantic button mask followed by six IEEE-754 binary64 little-endian values: left X/Y, right X/Y, left trigger, right trigger. Bits 0–16 follow the frozen gamepad-v1 schema order: south, east, west, north, leftShoulder, rightShoulder, leftTriggerButton, rightTriggerButton, select, start, home, leftStickPress, rightStickPress, dpadUp, dpadDown, dpadLeft, dpadRight. Other bits are rejected. Axes must be finite in [-1,1]; triggers finite in [0,1]. These are semantic values before hardware quantization. Unknown semantics require a new negotiated packet version; extending an enum cannot silently change this mapping.

The 96-bit GCM nonce is a session-provisioned four-byte prefix followed by the header sequence's eight little-endian bytes. Header bytes are associated data. Ciphertext is followed by the full 16-byte GCM tag; the nonce is not separately transmitted. Key, prefix, session and generation come only from a future authenticated native TLS grant. Every grant uses a fresh random 256-bit key. Do not derive a key from the pairing code, session ID, address or timestamp. No keys or counters are persisted/resumed. A new transport connection or activation requires fresh grant material.

One noncopyable-by-interface native sender instance owns a counter starting at zero and seals at most 2^20 packets per grant. A policy may reduce that limit. It consumes a nonce before invoking encryption, never resets the counter, and retires on cryptographic failure or explicit close. Session admission must additionally cap grant lifetime to ten minutes and bind trust/owner leases; the packet codec alone does not implement that clock policy. The native PacketRuntime adapter enforces the ten-minute cap and delegates lease/held-input expiry to the retained native safety owner. TLS fallback must send the same already-sealed packet bytes, never construct a second sender with the same grant. Retransmission of identical bytes is harmless but never renews held-state expiry.

A receiver advances its high-water mark only after tag verification and full semantic validation. Duplicate/reordered packets, wrong sessions/generations, invalid authenticated plaintext and failed tags do not return a state or advance the mark. Newer full states repair lost releases. Receiver close is terminal. Keyed packet validation alone does not grant input: the receiver session gate must still enforce trust revocation, native lease/input TTL, configuration acknowledgment and neutral restart.

Use CryptoKit, Android JCE AES/GCM/NoPadding and RustCrypto aes-gcm 0.10.3 (compatible with the pinned Rust 1.88 toolchain). The latter includes the fix for [RUSTSEC-2023-0096](https://rustsec.org/advisories/RUSTSEC-2023-0096.html); allocation-returning decryption releases no failed-tag plaintext to callers. Newer aes-gcm 0.11.1 resolved an aes dependency requiring Rust 1.89, so it is not used with the current baseline. No cryptographic primitive is implemented in application code. [RustCrypto usage](https://docs.rs/aes-gcm/0.10.3/aes_gcm/), [CryptoKit AES.GCM](https://developer.apple.com/documentation/cryptokit/aes/gcm) and [Android GCM parameters](https://developer.android.com/reference/javax/crypto/spec/GCMParameterSpec) define the primitive interfaces. Shared deterministic fixtures use public test keys and an independent Node crypto oracle; they are not enrollment secrets.
