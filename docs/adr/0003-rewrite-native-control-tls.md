# Native control TLS and bounded framing

Status: accepted for isolated headless implementation and interoperability tests. Product enrollment and a production listener remain pending.

The native receiver library owns host-authenticated TLS 1.3 through rustls with its Ring cryptography provider. A phone invitation must supply a SHA-256 pin of the complete DER leaf certificate, encoded as 64 lowercase hexadecimal characters. The client checks that exact certificate, refuses intermediates, and additionally validates the certificate name, validity period, server-auth usage and handshake signature with rustls/webpki. The fixed server name is `thumble-rewrite.local`; the required ALPN is `thumble-rewrite-control/1`. IP addresses are connection routes, not certificate identities. Wrong or missing ALPN and TLS 1.2 fail. Early data, tickets and session resumption are disabled.

An isolated `ServerIdentity` generates a fresh self-signed identity, valid from five minutes before creation through thirty days after creation. Its public certificate and pin are inspectable; private key bytes are not exposed by its public getters. Loading an existing identity requires a future native private-storage owner. This ephemeral generator does not implement stable device identity, rotation or secure credential persistence.

TLS authenticates the host. It does not authenticate a phone or authorize input. The server entry point is explicitly named `accept_unenrolled`; only a future versioned enrollment protocol may consume a local pairing window, commit phone trust and issue fresh packet grants. The transport currently exposes no product LAN listener and does not change CLI/service authority routing. No received control payload is automatically interpreted as configuration, trust or input admission.

After the handshake, each application frame is a four-byte unsigned big-endian length, a one-byte kind and payload. The length includes the kind. Kind 1 is opaque control data with 1–65,536 payload bytes. Kind 2 contains exactly the already-sealed 108-byte input packet from ADR 0002. Unknown kinds, zero/oversized lengths, wrong input size, truncation and I/O errors terminally close the channel. Length validation occurs immediately after the four-byte prefix. TLS fallback must carry existing sealed packet bytes; it cannot reuse a grant through a second encryption sender.

TCP connect and TLS handshake each have a three-second absolute deadline. Each frame operation has a two-second absolute deadline and a 128 KiB network-read budget, including TLS overhead. Time remaining is recomputed for every underlying read/write, including work inside rustls; trickled traffic cannot reset a deadline. Accepted sockets are explicitly normalized to blocking mode. Blocking transport operations belong on a bounded network worker independent of the existing ten-millisecond native safety loop. This library alone does not establish that worker topology, session admission limits or production latency acceptance.

The `control_tls_probe` example is a synthetic loopback-only engineering executable, excluded from packaged product binaries. It prints public certificate metadata, uses public deterministic fixture keys, and feeds input packets only into the recording backend. An independent Node/OpenSSL client exercises real TLS, framing, packet admission, semantic rejection, replay rejection and neutral repair. Separate connections verify wrong-pin and TLS-downgrade rejection. Rust tests additionally cover certificate policy, ALPN, framing limits, slow peers, byte budgets and terminal errors. Hosted evidence for earlier packet source must remain distinct from later TLS source until this slice is separately published and tested.
