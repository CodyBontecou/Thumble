# Native phone trust ledger

Status: implemented as an isolated native storage and TLS-delivery port. The native enrollment coordinator now consumes this port (ADR 0006); product listener/CLI forwarding, phone secure storage and active-session revocation integration remain pending.

A trusted phone has a stable opaque public identifier and a random 256-bit bearer credential. The identifier is not a public cryptographic key. Possession of the credential authenticates the phone only inside a channel whose host certificate has already passed the pinned TLS policy. No asymmetric phone signature or mutual TLS scheme is implied. The host stores a domain-separated SHA-256 verifier bound to its certificate pin and the phone identifier; it does not retain the bearer secret in the database. Credential epoch increases on re-enrollment and is separate from activation generation and input sequence.

`PhoneTrustStore` belongs to the native receiver authentication domain. It requires an existing persistent host identity, holds an exclusive owner lock, and uses `phone-trust.sqlite3` in that identity's private directory. JavaScript profile/catalog storage is a separate authority. This implementation uses pinned rusqlite 0.40.2 with bundled SQLite 3.53.2. Windows inherits the existing owner/SYSTEM private-directory policy and reparse refusal; Unix requires private files and rejects extra hard links. Existing database and journal files are bounded and checked before opening. Unknown application/schema versions, foreign databases, host-pin mismatch and corruption fail without rebuilding or silently adopting them.

The version 1 STRICT schema contains one host-bound clock record and at most 32 phone entries, including revoked tombstones. Each entry stores bounded identifier/label, positive credential epoch, revocation state, verifier, expiry and update time. Revocation removes the verifier. Credentials expire after thirty days; authorization rejects the exact expiry boundary. Enumeration exposes metadata only. An active metadata flag means not revoked; it does not override expiry or grant input.

Enrollment uses an immediate SQLite transaction. It validates the phone, generates native entropy, checks the capacity/epoch limit, updates the verifier and observed native wall clock, and commits before returning a native credential object. The crate-private `enroll_after_pairing` API has an explicit trusted-caller precondition: the native enrollment coordinator first consumes the one-use pairing window on the authenticated TLS connection. There is no agent-facing enrollment bypass or public listener. ADR 0006 describes the coordinator; its service forwarding remains pending.

The issued credential has no Debug/Serialize implementation or secret export getter. Its enrollment reply can be sent only through an open server-side `ControlChannel` presenting the same host pin as the ledger. The reply carries version 1, command `enrolled`, phone identifier, credential epoch, expiry and the credential inside TLS. A failed delivery reports unconfirmed delivery and retains committed trust; it never rolls the database back after sending might have begun. Until a separately specified retry protocol exists, recovery requires a fresh locally authorized pairing window. The phone must persist the credential in its OS secure store before acknowledging enrollment; that phone-side operation is not implemented here.

Authentication compares a fixed-size verifier in constant time and checks identity, revocation, expiry and clock monotonicity before returning metadata. Native wall-clock milliseconds are trusted-local inputs, never peer timestamps. Enrollment/authentication reject rollback relative to the stored observation. Revocation remains possible during rollback and preserves the maximum observed time. Storage errors deny authorization. These operations do not create input sessions: the future native session owner must bind grants to credential epoch, release output on revocation and retire stale authorizations before accepting input.

SQLite uses DELETE journaling, synchronous EXTRA, disabled trusted schema, enabled foreign keys, a 256-page cap and an immediate failure on lock contention. Transactions preserve the previous credential/epoch on failure. Process interruption fixtures and SQLite rollback tests establish the tested storage behavior; they do not establish physical power-loss durability on release filesystems. No memory-erasure guarantee is claimed for native allocations, TLS buffers or database page history. The raw randomly generated bearer secret is absent from database/public metadata fixtures.

Tests cover persistent authentication, wrong credentials/identity, expiration, clock rollback, re-enrollment invalidating old credentials, durable revocation, bounded capacity, invalid labels/identifiers, transaction abort, exclusive ownership, host binding, schema/corruption refusal, Unix link rejection and a real native TLS enrollment reply after commit. Wrong-role TLS delivery refuses to export the secret. Local checks include 43 native Rust tests, Clippy, 67 TypeScript tests (one explicitly skipped), standalone packaging and independent Node/OpenSSL TLS interoperability. Hosted evidence for earlier snapshots does not cover this new ledger or its persistent-host-identity dependency.

The bearer-secret confidentiality requirement follows the principle described in [RFC 6750](https://www.rfc-editor.org/info/rfc6750/); this native protocol is not OAuth. Transaction/durability choices use SQLite's [atomic commit design](https://www.sqlite.org/atomiccommit.html) and [synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous), through rusqlite's [explicit transaction behavior](https://docs.rs/rusqlite/0.40.2/rusqlite/struct.Connection.html#method.transaction_with_behavior). Platform secure storage, compatibility negotiation, enrollment coordination, listener lifecycle, input-session revocation, credential rotation/recovery UX and physical device tests remain separate gates.
