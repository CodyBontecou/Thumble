# Rewrite pairing and input transport

Status: accepted engineering direction; real-input enablement requires implementation review and the M1 signing/gameplay gates.

The rewrite uses an explicit one-use, 256-bit out-of-band pairing secret with a short pairing window. A QR code or complete text invitation binds the intended authority identity, pinned host certificate fingerprint, manual address and secret. A six-digit code would require an independently reviewed PAKE; we do not send a short password over an unauthenticated connection. Discovery supplies hints only. An invitation cannot be constructed or redeemed over the network until the pinned native TLS endpoint exists.

Use TLS 1.3 with exact host pin verification for pairing, control and reliable input fallback. Disable early data and unauthenticated certificate exceptions. The native phone validates the pin before sending the bootstrap secret. The host accepts one invitation once, binds enrollment to the authenticated TLS connection and phone public identifier, and commits trust before acknowledging it. Persist credentials only in platform secure storage and host user-private trust storage. Service restart invalidates unfinished windows. No old production credential or discovery namespace is reused implicitly.

After authenticated enrollment, the native receiver grants a short-lived input session bound to the trusted phone, host instance, activation generation and configuration receipt. A fresh random 256-bit AES-GCM key and separate direction nonce prefixes are provisioned only inside the authenticated channel. UDP uses an authenticated fixed header and a monotonically increasing counter nonce; reliable fallback uses the same session/generation/sequence acceptance rules. Keys never cross the React sample queue. Rekey before counter exhaustion; new connections, restarts and generations get new session material. Never reuse a key/nonce pair. The wire layout and cryptographic golden vectors must be fixed before enabling either network path.

Newest full-state samples repair lost releases. Duplicate or reordered samples do not advance held-state expiry. Fallback switches do not reset the sequence or revive an expired session. Native expiry and explicit revocation release held output independently of JavaScript; reconnection starts neutral under a fresh generation. Pairing grants configuration trust only after policy approval, and never authorizes production input by itself. Input, document, control and capabilities negotiate independent versions; unsupported mandatory semantics fail closed.

Pairing windows are bounded to one per authority instance, 120 seconds and five failed proof attempts. Cancellation, replacement, expiry, attempt exhaustion and clock rollback invalidate the window. Status contains no bootstrap secret or verifier. Issuance returns the secret once over authenticated same-user IPC. Admission must come only from the future native pinned TLS adapter; no local command for remotely claiming trust exists. The existing service pairing-window implementation has no network listener. A native transactional trust ledger (ADR 0005) and native TLS enrollment coordinator/window owner (ADR 0006) now exist, with shared fixture coverage. CLI/service forwarding to that native owner remains pending; the two owners are not silently connected. Native proof consumption remains a precondition for the crate-private trust operation. The phone identifier is opaque, and authentication uses a random bearer credential rather than an asymmetric phone key.

The retained wire oracle remains `Host/crates/thumble-protocol/src/wire.rs` (protocol 3 compact inputs, `PP` magic, bounded unique JSON), its Swift/Android counterparts and existing golden fixtures. Rewrite mobile transport negotiates its own version and discovery identity; it must not treat unauthenticated retained frames as authenticated rewrite input. Migration or compatibility needs an explicit tested adapter.

This chooses a high-entropy transfer workflow over a convenient short display code and preserves native input scheduling over an all-JavaScript network path. TLS follows [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446); native implementations use reviewed platform crypto APIs, including [CryptoKit AES.GCM](https://developer.apple.com/documentation/cryptokit/aes/gcm) and an equivalent Android/Rust implementation. TLS pinning, enrollment persistence, UDP framing, revocation integration and physical delivery remain implementation requirements, not claims established by this ADR.
