# Explicit native phone editor SDK

`PhoneEditorSession` composes the internal journal coordinator with the retained certificate-pinned TLS transport and native credential vault. It is created only by explicit editor APIs. Opening a session loads the protected native journal on its owner executor without connecting. A corrupt or concurrently changed journal rejects; it is never silently reset. Input connections and `PhoneConnection` are unchanged.

The app registry accepts no endpoint arguments. It reads only the existing saved pairing schema, reserves a single host journal owner, and returns a random session handle. Closing invalidates that handle immediately, cancels IO, and preserves the reservation until the old asynchronous operation actually settles. Cancellation of an older Kotlin future cannot cancel a newer call. Swift cancellation fences requests that have not yet crossed the coordinator actor boundary.

The fixed module methods are `editorOpen`, `editorSnapshot`, `editorCachePage`, `editorCatalog`, `editorRead`, `editorSelect`, `editorEnqueue`, `editorSubmit`, `editorReconcile`, `editorCancel`, and `editorClose`. The new `openEditor` React Native facade exposes the same operations with immutable bounded results. It does not create an editor screen.

Snapshots contain at most eight cache summaries and 128 queued entries. They contain no controls. `cachePage` returns at most eight controls for one native opaque context. Contexts are scoped to the current native session and exact cached profile. Enqueue requires that context, displayed revision, displayed source hash, control ID, operation ID, and nullable label. Native code checks both displayed pins against the currently retained cache and constructs the immutable intent itself. No JavaScript method accepts an authority, host, port, pin, phone epoch, storage path, verified read, receipt, or acknowledgment.

Explicit catalog/read/submit/reconcile calls resolve the current authority through the existing pinned resolver. Old queued origins remain immutable after restart. A changed authority produces `origin-reconciliation-required` before role-12 transport; it never redirects an old operation. Verified cross-restart origin handoff remains a future gate. Submit persists uncertainty before transport; cancellation or close never clears the queue. Receipts do not advance the profile cache.

SDK fake-IO tests cover offline enqueue durability, bounded pages, revision/hash mismatch, restored origin refusal, corruption refusal, and cancellation ownership. Existing coordinator/frame tests retain durable-before-offer, complete pinned reads, credential epoch, strict bounds, late callback, and cancellation coverage. App pod/module compilation verifies actual Expo registrations. These checks do not establish physical-device, live-game, or production host-role acceptance. Host role-12 policy activation remains independently gated on authenticated owner admission, acknowledgment/drain fencing, and cross-layer proof.

The draft role-12 hello and authenticated admission require both `inputEnabled: false` and `inputSessionAvailable: false`. Swift and Kotlin validate the exact shape; missing, true, and extra fields reject. Their hello fakes now read the shared `helloReply` vector in `phone-editor-control-v1.json`, aligning the unpublished draft SDK with the native host contract.

The opt-in `realServiceEditorUsesPinnedTLSAndExactReceipt` witness uses the retained Swift RPC/coordinator/session and actual pinned TLS against the real recording service, Rust admission policy, native host, and SQLite owner. A private synthetic credential source replaces Keychain for this test. It reads revision three, commits one label, reconciles its exact revision-four receipt, proves exact replay stays at revision four, and reads the updated label. This establishes that composition with synthetic credentials; it does not establish the production vault, physical device, or input/game acceptance gates.

Swift cancellation blocks fresh admission until the prior cancel call returns, including an idle cancellation. The registry requires its own close-returned barrier and the SDK's closed-and-drained query before replacing an owner; this does not rely on actor scheduling order.
