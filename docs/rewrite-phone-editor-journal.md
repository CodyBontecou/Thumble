# Native phone editor journal preparation

This SDK slice provides a bounded private edit journal and a separate cached profile read model. It does not register an editor wire role, expose a JavaScript acknowledgment method, send writes, or provide an editor screen. The sole SQLite writer remains the configuration owner.

An immutable label intent binds host certificate SHA-256, origin authority instance, operation ID, expected configuration revision, profile UUID, control UUID, and nullable label. Empty string means explicit blank; null removes the override. A/B/A profile navigation changes cached selection only and cannot redirect edits. Reusing a queued operation ID with changed intent fails. The caller must retain an uncertain operation ID and reconcile it rather than manufacture another edit.

Limits are 128 entries, eight cached profile contexts, 128 controls per context, and 2 MiB of canonical UTF-8 state. Profile names allow 256 Unicode scalars and 1,024 UTF-8 bytes; labels allow 128 UTF-8 bytes. Counters are canonical unsigned 64-bit strings. Decode checks depth and graph bounds before parsing, exact keys, duplicate-key rejection through canonical byte comparison, Unicode validity, identities, and aggregate limits. Existing malformed or foreign-host data blocks opening; it is never reset. Cache capacity exhaustion is explicit; there is no implicit eviction or credential storage.

## Receipt and read provenance

Internal `VerifiedEditorAcknowledgment` and `VerifiedEditorRead` types are composition assumptions, not authentication proofs themselves. No network factory exists here. A future authenticated client must verify complete revision/source-pinned read pages before minting a read and validate the original successful owner receipt against the exact sent intent before minting an acknowledgment. Raw JavaScript data must not enter these paths.

Retirement requires the exact queued intent, receipt operation ID, current authenticated session, response scope, exact affected profile/control pair, valid content hash, and resulting revision exactly expected plus one without overflow. An authority change additionally requires explicit verified origin reconciliation; otherwise the old entry stays queued. A historical receipt remains usable after current storage advances but cannot update cached profiles. Separate reads reject rollback and contradictory content at the same revision. Conflict, rejection, transport uncertainty, and ordinary snapshots retain entries.

## Persistence and uncertainty

Candidate persistence precedes the visible memory swap. Definitive pre-replacement failures preserve old disk and memory state. Post-replacement failure may leave complete old or new disk state: the SDK reports uncertainty, retains candidate bytes and operation identity, leaves visible memory unchanged, and blocks mutations until a full reopen validates disk. No automatic reset or retry with a different ID occurs. A verified acknowledgment may already have retired its exact entry in a valid reopened new state; it must not be reapplied as profile state.

The iOS provider uses a fixed application-support child. Only the trusted OS parent is resolved with POSIX `realpath`; private child and caller-selected test paths retain anchored component-by-component no-symlink checks. Files are owner-only, regular, singly linked, and directory-relative. A per-host lock and old-byte comparison fence stale writers. On iOS, staged files receive `completeUntilFirstUserAuthentication` protection before publication. File sync precedes rename; directory sync and full readback follow. A post-replace error latches uncertainty.

Android preserves API 26 support by passing the public Android 8.0 NDK close-on-exec flag value through public `Os.open`; it does not access the Java constant added in API 27 or hidden APIs. Android uses a fixed `noBackupFilesDir` child, owner-only files, per-host lock, old-byte comparison, and platform `AtomicFile` recovery. Candidate bytes sync before `finishWrite`; directory sync and canonical readback follow. `AtomicFile` can log rather than throw some finish errors, so readback is required. Failure to prove old unchanged state or complete successful candidate is uncertainty. App-private storage is the trust boundary; this does not protect against a malicious process with the same app identity.

Tests cover pre/post-replacement faults, competing writers, corrupt and aliased files, receipt mismatch, bounded caches, and shared synthetic A/B/A state. The macOS subprocess witness kills the actual Swift adapter at replacement boundaries and validates whole old/new state on reopen. This is process-kill coverage, not a power-loss guarantee. Android instrumentation executes the actual private provider on an API 35 emulator and checks its held lock descriptor has the close-on-exec flag through its own bounded `/proc/self/fdinfo` view. A separate API 26 CI job requires the exact named test and zero failures/skips before accepting a sanitized summary; API 26 execution remains pending until that job runs. JVM tests alone do not establish provider behavior. No credentials, endpoints, capture images, or input packets are stored.

Swift intent/profile aggregates use immutable small value wrappers with copy-on-write arrays. Required retained stack-safety verification remains an integration gate.
