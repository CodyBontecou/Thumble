# Explicit physical phone control v9

Control9 is an explicit native SDK opt-in for an already configured macOS HID receiver. It does not create a device, install/sign a helper, change the receiver backend, or activate saved configuration. Existing control3–6 clients remain recording-only and reject physical replies. Control7 catalog and control8 saved-map connections remain read-only management roles with unchanged JSON shapes.

The request hello has exactly version1, command `hello`, controlVersion9, role `physical-input`, requiredOutputBackend `macos-hid`, and input/document/capabilitiesVersion1. Its exact response echoes those fields plus authorityInstanceId. It omits `inputEnabled`: the hello expresses intent before credential proof and native inspection. A missing/wrong/null role or backend, an unknown field, or intent attached to an older version is rejected before authentication/enrollment effects.

After credential proof, the native owner inspects actual receiver output status. Recording cannot satisfy physical intent. The authenticated/control-status/disconnected metadata adds `outputBackend:macos-hid` and carries the receiver's actual `inputEnabled` boolean; source identity, credential epoch, connection binding and expiry remain independently checked. Configuration adds the same backend and requires admitted output when active. A physical grant or renewal requires `inputEnabled:true`, exact native generation/revision, actual output admission and the existing trust fences. Progress attests the exact still-live source; lost admission fails closed and cannot restore touches. Release carries the physical backend with `inputEnabled:false` and remains possible after device admission is lost.

The capability-authenticated native IPC retains its existing192-byte cap. Legacy STATUS1 remains exactly17bytes; operations1–6 continue to reject physical backends. New OUTPUT_STATUS7 returns the existing saved-status body followed by backend byte (0 recording,1 macOS HID) and admitted byte (0/1), totaling20 or128bytes. Read-only saved-map handling uses this output-aware status to pin layout metadata on either backend. Separate PHYSICAL_GRANT8, PHYSICAL_PACKET9, PHYSICAL_RELEASE10 and PHYSICAL_ROTATE11 retain the existing operation payloads and reply sizes. Grants/packets/rotation require actual physical admission; release remains usable for cleanup. IPC disconnect cleanup remembers the operation mode, and reconnecting a cleanup worker retains physical intent.

Both SDKs default to recording. Physical callers explicitly select `PhoneOutputMode.macosHID` in Swift or `PhoneOutputMode.MACOS_HID` in Kotlin and request input sessions, datagrams and renewals. Only that combination selects control9; no capability fallback or generic acceptance of `inputEnabled:true` occurs. Every configuration, grant, progress and renewal decoder receives this explicit mode, requires the exact physical backend and field set, and preserves the earlier recording-only schema when that mode is absent. Metadata may change admission state without changing its authenticated identity. Engine routes, encrypted108-byte packets, canonical20-byte reports, touch ownership, grant rotation, local deadlines,350ms input TTL and750ms owner lease are unchanged.

Shared `physical-input-control-v9.json` contains synthetic request/reply and grant/renewal vectors only. Native tests use fake output status/sinks and real loopback IPC/TLS where applicable. SDK tests use fake credentials/transports and the actual native engine without creating an OS device or socket-based game controller. Earlier recording suites remain required. This establishes protocol/SDK plumbing; phone UI opt-in, real signed-device behavior, App Store validation and gameplay acceptance require separate evidence.
