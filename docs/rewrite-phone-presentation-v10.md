# Read-only phone presentation management v10

Control v10 is an explicit `management` role on a separate pinned-TLS connection. Durable phone credential admission and epoch/revocation checks remain native. It has no input session, grant, packet, profile write or activation command. Physical input v9 and its deadlines are unchanged. The trusted parent enables this bridge with `phone-presentation-enable`; the acknowledgement is `phone-presentation-enabled`. Legacy negotiation stays strict.

A connection accepts at most 65 sequential requests, one outstanding request at a time: `configuration-presentation` and `configuration-presentation-icon`. Requests are at most 2048 bytes; the existing two-second TLS idle/read deadline remains. SDKs must close after each metadata/icon batch and create a new connection for their next foreground poll. A separate global connection try-gate admits at most one reusable presentation peer, so two phones cannot each park an extra presentation worker alongside their input worker and consume the four-worker listener pool. A rejected peer closes before management admission with native reason `presentation_busy`; clients report a fixed cosmetic failure and leave input alone. This gate is never acquired by input.

Each request pins the installed controller's old configuration revision/source hash, profile ID, native generation/revision, byte-identical viewport, and old materialized `configurationSha256`. Light and dark are explicit; only the retained `base` bank is supported. No modifier bank, theme inheritance, arbitrary filename, SVG, whole source document or atlas is accepted. Metadata replies are at most 32 KiB and contain at most 64 exact control IDs, labels and optional icon references/names. Each label/name is at most 128 UTF-8 bytes, with no truncation. A missing icon reference means no observed icon for that control. Current `presentationRevision` and `presentationSourceHash` are separate from the unchanged installed input pin.

The sole configuration child must retain the exact successful old map projection under the complete source/epoch/viewport/materialized-hash key (at most 8 entries/512 controls). A phone-supplied digest is not an installation proof by itself. Missing, evicted or restarted proof, a different selected profile, or changed control IDs/actions/rectangles/haptics requires explicit reactivation; presentation cannot perform it. The current projection may supply labels and exact base light/dark icons only after proving input equivalence against that cached map. No rebase of active input is implied by a newer presentation revision.

Icon requests additionally pin the current presentation revision/source hash, control ID and icon SHA256. Only that referenced icon may be returned. Each response is at most 16 KiB, containing canonical base64 for one verified 32×32 PNG of at most 8192 decoded bytes. Actual bounded PNG decompression and resource lookup run in the configuration child; the native bridge also checks canonical encoding, dimensions, byte count and SHA256. The shared portable codec checks bounded encoding/container dimensions; it is not a replacement for the child's or SDK's complete PNG verifier. A full 256-square atlas never crosses the parent boundary.

The bridge shares a management-only operation gate with map reads, acquired before opening an ephemeral native IPC client. It queries the active exact saved binding before requesting child data and again before successful delivery. No input, policy or trust-store mutex crosses parent wait, native IPC or TLS writes. Final cached authorization/revocation checks happen under a brief input scope guard; the independent management delivery fence stays held through send. Revoke/reenroll mark the old scope dead and drop global locks before draining that fence. A configuration can still replace after the final query: the SDK must discard callbacks unless its installed map and epochs still match. A presentation update never authorizes an input packet.

Private events are `phone-presentation` and correlated `phone-presentation-reply` with a positive monotonic event ID and authority echo. One underlying configuration read remains bounded and busy after the two-second phone timeout until it settles under the existing explicit owner-health budget. Late replies cannot satisfy a newer request. Errors are the fixed `presentation_busy`, `presentation_timeout`, `presentation_unavailable`, `presentation_reactivation_required`, `presentation_unsupported_profile`, `presentation_response_too_large` or `presentation_stale`; they never retire input.

Freshness is `observed`, `stale` or `not-evaluated`, based on current applied acknowledgement and matching advancing observation identity. Cached acknowledgement alone, a screenshot, or transport receipt is not evidence of current game state or authenticated gameplay. Base labels/icons are the initial slice; modifier bank changes, arbitrary skins, animations and broader rendering remain separate work.

Native-to-React notifications are separate strict cosmetic unions: metadata contains bounded controls without image bytes; icon events contain one small verified PNG; errors contain only an allowlisted code and installed generation/revision/hash. They carry no endpoint, credential, input action or hit geometry. SDKs fence callbacks by attempt/session/map and verify PNG/hash before notifying. UI decoding does not grant input.

Tests use synthetic data and fake output only. Real pinned TLS covers metadata plus 64 icon reads on one connection, the 65-request cap, concurrent presentation-peer rejection, missing role and input-frame rejection, source replacement, revocation during parent wait, late replies, and a two-second unanswered presentation request while held input and owner renewal remain healthy. Codec tests cover duplicate/nested fields, counters, source identity, UTF8 limits, malformed base64 and digest mismatch. These establish protocol boundaries; real phone presentation/live-game acceptance is still required separately.
