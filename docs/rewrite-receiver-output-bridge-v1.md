# Explicit native receiver output bridge

The default receiver and review package record reports. Optional feature `output-bridge` adds only the confined output-owner interface and fake-device tests. Feature `output-macos` additionally compiles the macOS factory. Compilation, entitlement inspection and activation are separate operations; these changes do not establish signing, provisioning, consumer recognition or gameplay acceptance.

The native command is `run-macos-hid ABS_RUNTIME_ROOT --allow-physical-output`. It requires both explicit mode and literal flag before filesystem work. A default build rejects that mode with `physical_output_not_built`. The macOS factory remains dormant until an authorized receiver activation. Default `run` arguments and recording reports remain unchanged.

The receiver passes its fallible, sleep-inclusive absolute millisecond clock directly to the output owner. A shared high-water/fault latch prevents a status-only clock failure from silently recovering. The first sample shortens the output deadline to the minimum of owner lease and input TTL. Renewal preserves that input bound; source barriers preserve authority bounds. Confirmed retirement precedes replacement. Accepted activation generations and revisions are consumed even when output creation fails, so retries require a fresh status/CAS.

Activation waits at most 100 ms, retirement 50 ms, and sample/deadline operations 10 ms. These are caller acknowledgement budgets, not guarantees that an OS call returns. Missing completion, queue exhaustion or a closed worker latch `physical_output_restart_required`, synchronously close further worker admission, and require receiver restart. Late creation or IO cannot restore authority. Definite backend failures can recover only through a newer activation after confirmed cleanup. No second factory is admitted over uncertain retirement.

Snapshots report `backend: macos-hid` for this explicit mode. `inputEnabled` requires logical activation, matching worker owner/generation, confirmed ready state, a current deadline and no clock or completion fault. Inactive, expired, retiring and uncertain output never advertises admission. This field describes native admission, not proof of device recognition. The service rejects local debug samples carrying `allowRecordedInput` on a physical backend; that flag cannot authorize OS output.

`bun tooling/build.ts --with-macos-output` compiles the optional macOS backend without activating it. The ordinary build remains recording-only. Neither command signs or provisions the helper. Service start/run accepts `--output macos-hid --allow-physical-output`; both flags are forwarded explicitly to the service child and receiver. Flags on unrelated commands, a missing literal opt-in, and changing launch options on an existing service are rejected. Final-artifact verification remains required before an operational physical-output package is accepted.

Verification uses fake factories, clock faults, blocked creation/report calls, queue pressure, expiry inside native IO, handoff barriers and failed saved activation. Process tests invoke only rejected physical modes. All-feature compilation does not instantiate an OS device. Physical input, distribution signing, Windows backend adoption and all gameplay gates remain pending.

The current phone input wire explicitly asserts `inputEnabled: false`. Native ingress rejects every operation on a physical backend with `native_input_backend_not_supported`, so pairing or a recording-only phone grant cannot silently reach OS output. Physical phone capability/status negotiation remains a required integration seam; this slice is an explicit receiver prototype, not an operational phone gameplay package. A fake physical backend regression proves grant/status rejection while the receiver activation stays neutral and unchanged.
