# Native phone credential storage v1

The isolated phone libraries now provide an opaque native credential and a synchronous vault. The enrollment client must validate the TLS enrollment reply, construct the credential in native code, save it successfully, then send `enrollment-stored`. The native Swift/Kotlin enrollment clients now perform that sequence and require the host's control-v2 completion reply. The native control-v3 clients also load credentials through the vault/storage worker after pinned TLS hello validation; only native code constructs the authentication frame. Product phone-app wiring remains pending. Vault operations belong on a native enrollment/storage worker; input/UI sampling never schedules them. No credential or raw storage record is exposed through a React bridge or general JSON/Codable API.

The record is `THPC1` plus three zero bytes, 32 certificate-pin bytes, one phone-identifier byte count, 1–64 ASCII identity bytes, little-endian positive signed-range 64-bit epoch and expiry, then 32 credential bytes. The exact size is 89 plus identifier length (90–153 bytes). Unknown magic, extra/truncated data, malformed identifiers and zero/out-of-range epochs/expiry fail. `phone-credential-v1.json` is a synthetic public byte fixture shared by Swift and Kotlin. Swift keeps the aggregate behind immutable storage and tests its inline size at no more than 16 bytes; Kotlin copies secret buffers and provides no generated data-class token methods. Description/debug/reflection output is redacted in Swift; Kotlin's credential string is redacted. Native allocation memory erasure is not promised.

Saving checks the existing record and its host binding. For the same phone, older epochs and equal epochs with changed content are rejected; an exactly equal record is idempotent. A new credential is acknowledged only after storage write and exact readback succeed. A failed write/readback does not erase potentially committed storage. Loading rejects the exact expiry boundary, malformed/misbound records and unavailable storage. Missing credentials are distinct from errors. Forgetting one pin does not delete another host's credential or unrelated retained profiles. Corruption/key invalidation requires explicit recovery; no retained credentials or namespace are silently imported.

The Swift backend uses generic-password Keychain records under `com.thumble.rewrite.phone-trust.v1`, account equal to the certificate pin, synchronization disabled, the data-protection Keychain, and `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`. A fresh LocalAuthentication context has interaction disabled. OS errors are reported as unavailable, with no interactive prompt or fallback storage. One process-wide lock serializes read/check/write/readback across vault instances. No cross-process or extension-sharing protocol is claimed. The simulator-only entitled test host now verifies actual persistence and stored accessibility/synchronization attributes locally. The original hosted package test failed without application entitlements; the reviewed test-host CI repair still needs publication/runner execution. See Apple's [Keychain accessibility reference](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly).

The Android backend requires API 29+, matching the isolated TLS adapter's current requirement; this does not settle the final launch OS matrix. It writes only encrypted records under the application's `noBackupFilesDir/rewrite-phone-trust-v1`, with private directory/file permissions, regular-file/link checks, bounded reads and one exclusive file lock spanning each operation. AtomicFile publishes the encrypted record. AES-256-GCM uses a provider-generated 12-byte nonce, 128-bit tag and associated data binding the separate namespace and certificate pin. The nonexportable key is generated through AndroidKeyStore with randomized encryption and unlocked-device requirements. A missing key with existing records fails rather than generating a replacement. Forgetting one record leaves the shared encryption key available for other hosts. Explicit recovery/rotation UX remains pending. See the [Keystore guide](https://developer.android.com/privacy-and-security/keystore) and [AtomicFile reference](https://developer.android.com/reference/android/util/AtomicFile).

Local tests run real JCE encryption/tampering/pin/key/nonce checks and both language vault policies through transaction-checking storage doubles. They verify fixture bytes, immutable ownership, malformed records, epoch conflicts, read/write failures, uncertain readback, expiry, host binding and scoped forget. These doubles do not prove OS-provider persistence. The approved 07da0e0 snapshot passed the real Android Keystore instrumentation case on a headless API 35 runner. Its iOS package test failed with unavailable storage; local instrumentation confirmed errSecMissingEntitlement (-34018) in the hostless xctest process. The separate entitled simulator app host passes the same real Keychain case, including record policy attributes, against both current and isolated approved source. Hosted iOS verification awaits the scoped CI repair. They create only synthetic app-private credentials and clean up their own pins. SDK builds and Linux/JVM crypto tests do not replace iOS Keychain or AndroidKeyStore runtime evidence, credential-lock/device-lifecycle acceptance, power-loss behavior or physical gameplay gates.
