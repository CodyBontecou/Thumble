# Android reliable input backpressure

The launch phone control paths (v5, v6 recording and v9 Mac input) now bound encrypted TLS input writes to eight outstanding dispatches, including the socket write in progress, plus one coalesced unsent latest state. This addresses a measured physical Pixel failure: its display-rate samples outpaced the receiver's former roughly 11.5 ms per-packet IPC handling, so already-written TCP input bytes buried control requests. Local writer-queue bounds alone did not bound that TCP backlog. Actual phone diagnostics showed a receive deadline after all control writes completed, with the expected response still missing.

Only a strictly validated current connection/session/map input-progress receipt replenishes credits. The existing route validates sequence monotonicity and the highest sequence offered across both UDP and TLS. A UDP acknowledgement may legitimately exceed the highest TLS-only write; it cannot exceed the route's offered counter or unlock a different grant.

Enqueuing a control transaction pauses further input dispatch under the same gate used to select writes. Control frames remain FIFO. Its strictly validated reply therefore proves consumption of preceding input writes. During renewal, the old credit window is retired only after that reply validates, while the barrier remains held. The native input owner then queues fresh packet zero, discarding the old unsent latest state, before unpausing. Packet zero cannot reset an old window on its own. No report is resealed and counters are never rewound.

Both packet zero and the coalesced latest state retain their original offer time. A queued input at or beyond the unchanged 350 ms freshness limit is rejected before dispatch. Production uses the phone owner's existing continuous elapsed-clock port. Closing clears pending data and cannot be reopened by an acknowledgement; a socket write already reserved before closure remains within the eight-dispatch bound.

The existing 100 ms progress cadence, 2-second TLS deadline, leases, grants and receiver input TTL are unchanged. Legacy v4 retains its existing delivery and 1-second status cadence because it has no input-progress ACK contract; an eight-credit policy cannot be added there without a separate compatibility design. Generic data-only TLS adapters also do not implicitly acquire the admitted-input credit policy.

Tests cover pressure beyond eight dispatches, coalescing, a write active when a control barrier is queued, rollover with a full old window, invalid and UDP-advanced acknowledgements, stale queued states, close/cancellation and legacy v4 behavior. Real native probes cover actual TLS/input/IPC and both 75-second automatic-renewal transport modes. Physical sustained-session verification and Swift parity are separate acceptance gates; instrumentation alone was not treated as a reliability fix.
