# Headless native pairing owner

The service now forwards pairing operations to a separate native owner through private inherited stdio. The TypeScript pairing state machine remains a fixture oracle and is not elected as a runtime fallback. Default service startup creates local-only native bootstrap windows, preserving the existing CLI behavior. Listening requires an explicitly initialized persistent identity and an explicit manual bind/advertisement request. Controller output remains recording-only and disabled for real input.

Initialize once, then configure service startup with the same absolute identity directory:

```sh
thumble-rewrite identity initialize --identity-dir /absolute/identity --json
thumble-rewrite service start --runtime-dir /absolute/runtime --identity-dir /absolute/identity --json
thumble-rewrite pairing listen --runtime-dir /absolute/runtime --bind-address 0.0.0.0:0 --advertise-host 192.168.1.50 --reveal-secret --json
```

Replace the sample LAN address with the computer's address reachable by the phone. Port zero allocates an ephemeral listener port; the reply reports the actual bound address/port. Bind addresses are numeric IPv4/IPv6 socket addresses; advertised hosts are bounded manual IP/hostname strings. No discovery or retained address namespace is elected automatically. Without configured persistent identity, listen returns `pairing_persistent_identity_required`. Initialization never runs implicitly during listener setup. Starting against an existing service with an explicit identity requires its host pin to match; changing storage/setup requires stopping the old owner first.

The secret-bearing offer contains the complete native phone invitation: host, port, certificate pin, authority instance, window identifier, secret and expiry. Open/listen require `--reveal-secret`. Status omits the offer and secret; its public transport metadata includes listener state, bind/advertised addresses, public certificate DER/pin, persistent-identity flag, fixed server name, control version 2 and `inputEnabled:false`. Public DER permits independent normal TLS validation; private key bytes remain in the native process/storage. Native phone clients still verify the certificate/pin before proof. This CLI does not create an input session or a React Native application.

`pairing open` replaces the window and returns a full invitation when a listener is active, or the local-only bootstrap offer otherwise. `pairing cancel` cancels the window while preserving listener configuration; it prevents prospective enrollment and does not revoke committed trust. `pairing stop-listening` cancels the window, stops acceptance and closes accepted/queued transports. Cancellation/replacement during a TLS wait is effective before proof consumption. A native mutation lock serializes proof consumption plus the trust commit with revocation; it is released before credential delivery. Native store operations use short locks; neither policy nor trust-store locks are retained while waiting on TLS. A window retired before its offer snapshot is captured produces an error, not a contradictory secret-bearing reply.

The native host uses four fixed network workers and a four-job queue, with at most eight registered sockets. Listener replacement creates only the accept loop; the worker pool is reused for the native owner's lifetime. Accept loops are nonblocking and bounded per iteration. Existing TLS handshake/frame byte limits and absolute deadlines apply. Native parent EOF, private-pipe backpressure, listener shutdown and process termination fence pending windows/transports. In-flight storage may remain committed after ambiguous delivery; credentials/windows are never silently rolled back or replayed.

The listener closes the control channel after the control-v2 enrollment completion exchange. It also accepts native credential authentication and bounded status/disconnect on control version 3; see [the authenticated control contract](rewrite-authenticated-control-v3.md). Native Swift/Kotlin authentication clients use that exchange; input-grant handoff remains pending. The input safety receiver remains a separate native child with its own monotonic lease/TTL. Pairing socket work cannot delay its native safety loop. Pairing-owner failure stops the service; service/owner loss closes inherited pipes and neutralizes the receiver through the existing independent safety path. No desktop GUI or desktop IPC participates.

The same packaged CLI/native binary launches both native roles. Tests run the source CLI and standalone executable outside the checkout with Bun removed from the executable's PATH. An independent Node/OpenSSL test peer validates normal TLS 1.3, fixed name/ALPN and exact certificate pin before sending the synthetic proof. Tests cover enrollment, cancellation after hello, default refusal without persistent identity, configuration mismatch, secret-free status and service death with a stalled TLS peer. Native tests also exercise bounded socket acceptance, store/policy responsiveness and listener shutdown. Node is a test driver, not a runtime product dependency.

This implementation is local and newer than the frozen 25-file phone/vault snapshot 8f216c9 awaiting separate CI approval. That snapshot excludes this host/listener/service work. The headless provider workflow and subsequent Windows/macOS/Linux verification need their corresponding approved source snapshots. Input-session authorization, native packet routing, authenticated reconnect, phone UI, LAN permission/firewall behavior, release signing, gameplay and optical acceptance remain pending. Retained functionality and native signing/rendering owners are not retired by this change.

## Trust inventory and revocation

`pairing list --runtime-dir /absolute/runtime --json` reports at most 32 sorted phone metadata records: phone ID, label, decimal credential epoch, active flag and expiry. The active flag records revocation state; a record can still be expired. No bearer token or verifier crosses the private native pipe. Ordinary pairing replies include the same inventory. Local-only services return an empty inventory.

`pairing revoke --runtime-dir /absolute/runtime --phone-id PHONE-ID --json` first releases the independent recording receiver, then cancels the current invitation, shuts down registered native TLS peers, and durably clears that phone's verifier. It closes peers again after the database operation. The listener remains available, but a fresh invitation is required for enrollment. The mutation lock ensures an older proof already waiting for storage cannot commit after successful revocation: it either commits first and is revoked, or observes the canceled window. Successful revocation survives service restart. Repeating revocation is allowed; an unknown phone reports `phone_not_found`. Storage failure still leaves the window canceled, peers closed and recording receiver released; callers must inspect the error and retry durable revocation. This currently fences all enrollment peers and recording output, rather than selecting a live input session. Authenticated version-3 control connections are also closed by revocation; their future per-phone input grants are not yet implemented.

The race regression deliberately blocks storage after proof consumption, starts revocation while enrollment holds the mutation lock, observes immediate TLS shutdown, then permits the old transaction and verifies the persisted record remains revoked across owner restart. CLI coverage checks metadata, durable revocation, held-state neutralization and neutralization even when the phone ID is absent. These newer trust controls remain local and are outside the frozen phone/vault CI candidate.
