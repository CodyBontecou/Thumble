# Pure Windows optical capture preparation

This independent, standard-library-only crate prepares a future native Windows optical provider. It contains no Windows API dependency, window enumeration, capture/session creation, permission prompt, PNG encoder, process query, receiver integration, or physical input/output. Its tests never create or capture a device/window. A successful gate establishes synthetic decoding and supplied-metadata policy, not actual WoW capture or process authentication.

`decode_panel(Raster)` borrows transient raster bytes with explicit RGBA/BGRA order, top-left/bottom-left orientation and row stride. It normalizes pixels when reading them; it does not allocate a second whole-window image. Only a checksum-valid 512-byte THWL page and a copied 256×256 top-left RGBA atlas leave the decoder, together from that single call. The atlas is raw RGBA, **not PNG**. A later reviewed native encoder and the portable capture codec's required real PNG verification port must be composed before a private capture reply is emitted.

Bounds match `Rewrite/packages/domain/src/wow-optical-panel.ts`: dimensions 1…8192, at most 16,777,216 pixels, stride between width×4 and width×4+4096, exact buffer length and at most 64 MiB. Discovery searches only the upper-left 512-square area, with 4,194,304 sample reads maximum; atlas copying adds a fixed 65,536 bounded pixel reads. Fiducials, calibrated grayscale, nearest-nibble tolerance, page structure/checksum and nearest-center atlas resampling follow that owned TypeScript implementation and the retained Swift oracle. Native image buffers stay private/transient.

`select_window` applies a pure policy to at most 128 supplied candidates: require exactly one visible, non-minimized, top-level eligible client window of usable bounded size and nonzero private identity. The `eligible_client` boolean is deliberately a **trusted future native adapter result**, not evidence established here. The future adapter must validate the actual selected WoW executable/client and query process/window metadata itself; filename or caller claims are insufficient. The current exact Windows Forever client identity remains an external launch decision. Candidates are not a public arbitrary-window capture interface.

`WindowIdentity` preserves a full uint64 window handle plus process ID, process-start identity and executable identity. It never truncates a Windows HWND into an observer source. `CaptureBinding` compares that complete supplied identity at decode and echoes the nonzero opaque uint32 source plus uint64 generation/receipt issued by the application supervisor. It advances no counters, owns no clock, and duplicates no supervisor lifecycle. Its identity comparison cannot authenticate caller-provided pixels; the real provider must privately bind and re-query identity around acquisition. Replacement, resize, scale/device changes, stop/timeout and delayed completion must still invalidate ownership through the supervisor and real provider.

Verification:

```sh
cargo +1.88.0 test --locked --manifest-path Rewrite/native/windows-optical/Cargo.toml
cargo +1.88.0 clippy --locked --manifest-path Rewrite/native/windows-optical/Cargo.toml --all-targets -- -D warnings
bun Rewrite/tooling/test-windows-optical-parity.ts
```

The five Rust tests use the curated synthetic `Rewrite/packages/fixtures/wow-live-v1.json` page (copied from the retained fixture) and generated pixels. They cover ten retained scales, four atlas corners, complete BGRA/bottom-up/stride parity, result ownership, corruption/clipping/invalid allocations, exact adversarial scan-budget exhaustion, ambiguous inventories, pointer-width identities and receipt/source replacement rejection. No captured user/game pixels are fixtures.

The separate Bun tool compiles only `examples/raster_oracle.rs` into a fresh temporary target directory and compares its complete binary page/atlas result with the actual TypeScript decoder across 24 generated cases: ten scales in RGBA and padded bottom-up BGRA, corrupted payload, tiny/clipped frames and the exact adversarial workload. The synthetic stdin witness admits at most 64 MiB plus its 20-byte header, emits only a fixed result category or page/atlas, and accesses no OS capture/window APIs. It is test tooling, not a capture command. Temporary builds are removed afterward.

Remaining Windows work requires a separately reviewed Windows.Graphics.Capture/Direct3D adapter, supported SDK dependency pin, strict client detection, actual protected/hidden/HDR/scaling/device-loss behavior, final permission/signing/distribution acceptance and physical phone/game testing. The intended API research is [CreateForWindow](https://learn.microsoft.com/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow), [CreateFreeThreaded](https://learn.microsoft.com/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded), and Microsoft's [capture/frame-lifetime guide](https://learn.microsoft.com/windows/apps/develop/media-authoring-processing/screen-capture). None is invoked by this crate. Manual snapshot refresh remains required when live observation is unavailable or stale.
